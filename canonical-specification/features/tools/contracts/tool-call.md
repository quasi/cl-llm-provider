# Tool Call Contract

This contract defines how tools are called by LLMs and how those calls are represented in the system.

## Overview

A tool call represents an LLM's request to execute a specific tool with given arguments. Tool calls are extracted from completion responses and contain all information needed for execution.

## Function: `tool-calls`

Extract tool calls from a completion response.

### Signature

```lisp
(tool-calls response) → list-of-tool-call-objects
```

### Parameters

| Parameter | Type | Description |
|-----------|------|-------------|
| `response` | completion-response | Response object from `complete` |

### Return Value

Returns a list of `tool-call` objects, or `nil` if no tool calls were made.

### Tool Call Object Schema

```json-schema
{
  "type": "object",
  "properties": {
    "id": {
      "type": "string",
      "description": "Unique identifier for this tool call"
    },
    "name": {
      "type": "string",
      "description": "Name of the tool to call"
    },
    "arguments": {
      "type": "object",
      "description": "Tool arguments as plist (:param value ...)"
    },
    "type": {
      "type": "string",
      "enum": ["function"],
      "description": "Call type (currently always 'function')"
    }
  },
  "required": ["id", "name", "arguments"]
}
```

## Tool Call Accessors

### `tool-call-id`

```lisp
(tool-call-id tool-call) → string
```

Returns the unique identifier for the tool call.

### `tool-call-name`

```lisp
(tool-call-name tool-call) → string
```

Returns the name of the tool being called.

### `tool-call-arguments`

```lisp
(tool-call-arguments tool-call) → plist
```

Returns the arguments as a plist (keyword-value pairs).

**Example**: `(:location "Paris" :unit "celsius")`

## Usage Example

```lisp
(let* ((tools (list (define-tool "get_weather"
                      "Get weather for a location"
                      '((:name "location" :type :string :description "City"))
                      :required '("location"))))
       (response (complete '((:role "user" :content "What's the weather in Tokyo?"))
                          :tools tools)))
  (when-let ((calls (tool-calls response)))
    (dolist (call calls)
      (format t "Tool: ~A~%" (tool-call-name call))
      (format t "Args: ~A~%" (tool-call-arguments call))
      (format t "ID: ~A~%" (tool-call-id call)))))

;; Output:
;; Tool: get_weather
;; Args: (:LOCATION "Tokyo")
;; ID: call_abc123
```

## Provider Response Format

### OpenAI Format

```json
{
  "choices": [{
    "message": {
      "role": "assistant",
      "tool_calls": [{
        "id": "call_abc123",
        "type": "function",
        "function": {
          "name": "get_weather",
          "arguments": "{\"location\":\"Tokyo\"}"
        }
      }]
    },
    "finish_reason": "tool_calls"
  }]
}
```

### Anthropic Format

```json
{
  "content": [{
    "type": "tool_use",
    "id": "toolu_xyz789",
    "name": "get_weather",
    "input": {
      "location": "Tokyo"
    }
  }],
  "stop_reason": "tool_use"
}
```

Both formats are normalized to the same internal `tool-call` structure.

## Invariants

1. **Unique IDs**: Each tool call in a response MUST have a unique ID
2. **Valid tool name**: The tool name MUST match a tool in the provided tool set
3. **JSON arguments**: Arguments from the provider are always JSON strings and MUST be parseable
4. **Plist conversion**: After parsing, arguments MUST be converted to plist format with keyword keys
5. **Finish reason**: When tool calls are present, finish reason is typically "tool_calls" (OpenAI) or "tool_use" (Anthropic)

## Error Conditions

| Condition | When | Recovery |
|-----------|------|----------|
| `malformed-tool-call` | Tool call JSON cannot be parsed | Log error, skip call |
| `unknown-tool` | Tool name not in provided tool set | Notify LLM of error |
| `invalid-arguments` | Arguments don't match parameter schema | Trigger validation error |

- Tool call IDs are generated by the provider and used to match results to calls
